# Test command contracts through cli.Run and the compiled binary

Rule ID: `local:techs/go/test-command-contracts-through-the-cli`

**When to read:** Before planning, writing, changing, or reviewing Go tests, or Go changes, that affect what a code-rules command prints, returns in --json, exits with, prompts for, refuses, or writes, including failures and interrupted writes.

**Impact:** HIGH

**Why it matters:** Helper-only tests pass while the assembled command writes to the wrong stream, exits with the wrong status, or leaves partial files, which breaks the contract agents and scripts depend on.

## Guidance

Prove a command's contract where the command is assembled.
Call `cli.Run` with test `Streams` to check standard output, standard error, and the exit status, in both human and `--json` modes.
Run the compiled binary for behavior that only a real process has.
Exercise refusals and interrupted writes through the production operation, not through a helper.

### Implementation

- In `internal/cli` tests, call `Run(ctx, args, Streams{Out: &out, Err: &diagnostic}, Options{Directory: directory})`, as `invokeReport` does, and assert the exit status, the human text, and the `--json` response's `ok`, `value`, and `error`.
- Build `cmd/code-rules` with `buildCLI` and run it with `runCLI`, `runCLIWithGit`, or `terminalfixture.Run` when the behavior depends on the process: the exit status `main` returns, prompts in a terminal, interrupts, `PATH`, or Git configuration.
- For a refusal, such as a usage error, a busy project, or a concurrent change, run the real command and assert both the documented code and that no file changed.
- For an interrupted write, stop the production `filetxn` transaction partway, as `interruptedUpdate` does, then run the next real command and assert that it recovers or finishes the files and that `code-rules project check` passes.
- Keep unit tests of helpers for the helper's own behavior. They don't replace a command-level test of the contract.

### Rationale

Agents and scripts depend on what a command prints, returns in `--json`, and exits with, and on the files it leaves behind when it fails.
Those behaviors come from several layers working together: Cobra's argument handling, `internal/cli`'s error classification and output modes, the domain operation, and `filetxn`'s transaction.
A test of one helper can pass while the assembled command writes to the wrong stream, exits with the wrong status, or leaves partial files.

### Examples

**Incorrect (counterexample):**

```go
func TestClassifyError_UnknownFlagIsUsage(t *testing.T) {
	if got := classifyError(usage(errors.New("unknown flag: --bad"))); got.Kind != "usage" {
		t.Fatalf("kind %q", got.Kind)
	}
}
```

The test passes even if `Run` exits with `1` instead of `2`, writes the error to standard error in `--json` mode, or prints human text instead of one JSON response.

**Correct:**

```go
out, diagnostic, code := invokeReport(t, ctx, directory, "project", "build", "--bad", "--json")
var result response
if err := json.Unmarshal([]byte(out), &result); err != nil {
	t.Fatal(err, out)
}
if code != 2 || result.OK || diagnostic != "" || result.Error.Kind != "usage" || result.Error.Code != "invalid-arguments" {
	t.Fatal(code, out, diagnostic)
}
```

The test checks the exit status, both streams, and the documented error code through the real command entry point.

### Validation

For a change to a command's output, error codes, prompts, or writes, check that a test reaches it through `cli.Run` or the compiled binary, in each output mode the change affects.
For a change to a write, check that a test covers its refusal and, when it adds a transaction target, an interruption followed by recovery.

Not a violation: a unit test of a parser, renderer, or other helper that checks only that helper's behavior.
