# Project operations

`internal/project` owns the complete lifecycle of a consuming project's Code Rules state:

- `Initialize`, `AddLocalGroup`, `AddLocalRule`, and `AddSource` create or update authored project state without fetching libraries or generating output.
- `PlanLocalGroup`, `PlanLocalRule`, and `PlanSource` check targets before prompts collect input; each plan's `Commit` revalidates under writer ownership.
- `Sync` imports all configured Git sources, validates and renders the full result, then installs vendor and generated files together. Each source's `vendor/<source>/_source.json` is its lockfile: sync restores the recorded rule versions and chooses versions only where configuration asks for something the record doesn't have. The record carries a checksum of its other fields, and `parseSourceRecord`, the one reader every operation uses, refuses a record whose checksum is missing or doesn't match, such as after a hand edit or a merge resolution; nothing records such a record again.
- `PlanUpdate` reads the project and the release history of each source the update names, without writing, and returns the preview from `imports.PlanUpdate`, which starts from what sync would import. Its `Apply` rechecks under writer ownership that configuration and vendor output are unchanged since planning, adds the decided pins and exclusions, and the new `basedOn` of each fork it replaces, to `config.yaml` with `rules.EditConfigurationSource`, and installs exactly the planned versions with `imports.Update.Import`, which first refuses when a library release tag they come from has moved since planning, replacing `config.yaml`, `vendor/`, `generated/`, and each replaced fork's local rule and asset directory in one transaction. A fork it replaces is read with `imports.ReadPublishedRule` before the transaction and laid out by the same `forkFiles` as `PlanFork`, at the exclusion's `replacedBy` path. The CLI collects prompt answers between planning and `Apply`.
- `PlanFork` reads one published version of a library rule with `imports.ReadPublishedRule` and prepares a self-contained copy for `local/`: the shared assets its Markdown links reach move into its asset directory with rewritten links, and attribution cites the rule at the library release's commit on GitHub.com and GitLab.com, or another host's HTTPS repository address. Its `Commit` rechecks the configuration under writer ownership and writes the copy, the library's group metadata when neither local metadata nor an imported source supplies the group, and, when that library's source selects the rule and its synced record imports it, the exclusion naming the fork as `replacedBy` and the forked version as `basedOn`, removing any pin of the rule, in one authored-file edit. The CLI asks for the exclusion's reason between planning and `Commit`.
- `Build` and `Check` load each source from its verified vendored bytes, stored at their library paths, and require the record to describe exactly those rules and files.
- `Build` verifies persisted source identity and original-byte digests, then regenerates offline.
- `Check` compares generated output and the managed project guide in one optimistic snapshot, without writes or Git access. It returns typed problems with config-relative paths and repair actions. Staleness is a report; invalid input or concurrent edits are errors. The CLI formats messages and repair commands and selects the exit status.

`Sync` passes the recorded snapshots to `imports.ImportLibraries`. Inside `imports`, sync and update each resolve a source into a plan of rule versions and commits, and one operation imports any plan: it fetches the plan's commits, validates the catalog, and builds the snapshot. Git revisions and temporary repository ownership stay private to `imports`, which runs Git through `internal/gitexec` in its isolated mode: hooks disabled and only HTTPS and SSH transports allowed. `imports` reads a library's `release/<number>` tags to choose versions, as it always does when planning an update, to find one, as when forking a rule, and, for a source that follows rule versions, to check that the versions and commits its record keeps still match those tags; a source that sets `ref` keeps the commit its recorded ref named, even after the tag moves. It fetches the tags as a partial clone with depth 1 and no blobs, then fetches in one request the blobs of the files it imports. Library-wide files come from one commit and each rule's files from the library release that published its version. `Build`, `Sync`, and update request complete output through `build.Generate`.

Snapshot encoding, guide rendering, file inventories, and the combined check machinery are private implementation details. Ordinary callers request complete project operations.

`internal/filetxn` owns the shared storage protocol. Its `WithWriter` and `Writer.Apply` operations hide lock ownership, interrupted-operation recovery, staging, installation, and rollback. `Writer.Apply` also accepts `config.yaml` as a target, which only update uses, so its pins and exclusions and the output they select are restored or finished together, `local/<group>/_group.yaml` targets, which sync and update create when local rules would lose the only imported copy of their group's metadata, and a local rule and its asset directory, which update replaces when it replaces a fork, removing the directory when the new fork has none. `Apply` changes nothing outside its transaction directory until the caller's recheck passes and the journal is written; only then does it create the missing parent directories of local rule targets, using a directory that appeared meanwhile and refusing anything else there. Nothing removes those directories again: a rollback, in `Apply` or in recovery, leaves them, empty, because a path can't prove who made the directory now there, and an empty directory under `local/` is harmless to every command. Preserve these deep operations rather than spreading their protocol across callers. Authored-file publication uses its separate `Edit` operation because exclusive creation and one guarded replacement differ from replacing whole managed trees. Both operations share writer ownership. Concurrent changes cause refusal before installation; once replacement begins, it completes or rolls back.

The [sync and recovery reference](../docs/src/content/docs/reference/sync.md) owns the filesystem contract and limitations. Tests include concurrent changes, malformed journals, cancellation, byte-exact retention, and failed multi-source sync. Run the [Go validation commands](../CONTRIBUTING.md#validate-changes).
