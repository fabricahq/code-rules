A library is a Git repository of groups and rules that projects can import. Use the `code-rules library` commands to create its files, or write them directly using the format below. Run `code-rules library check` before publishing.

## Library layout

<FileTree>

- engineering-rules/
  - rule-library.yaml
  - LICENSE.md
  - techs/
    - typescript/
      - _group.yaml
      - README.md
      - prefer-type-aliases.md
  - practices/
    - testing/
      - _group.yaml
      - README.md
      - verify-retry-limits.md

</FileTree>

The repository name is your choice. Put groups under `techs/` or `practices/`. Each group needs `_group.yaml`; each rule is a Markdown file in a group. A group's `README.md` helps authors but is not a rule. The rule's path without `.md` is its stable ID, such as `practices/testing/verify-retry-limits`.

Use lowercase letters, digits, and hyphens for group names, starting with a letter. Use lowercase letters, digits, dots, and hyphens for rule filenames and any subdirectories beneath a group. Rule paths must end in `.md`. Keep `assets` for supporting files, not group or rule names. Use forward slashes and paths inside the library; Code Rules rejects symlinks and path spelling collisions.

Declare the format and any library-wide license in `rule-library.yaml`:

```yaml
formatVersion: 1
license:
  spdxExpression: MIT
  file: LICENSE.md
  notices: []
```

A [library license declaration](#library-license-metadata) is optional in the file format. Choose and record terms before sharing the rules. A consuming project stores imported files in `.code-rules/vendor/` and prepares agent-readable files in `.code-rules/generated/`. See [Project files](/reference/files/).

## Group metadata

Put `_group.yaml` in each group directory. All three fields are required, non-blank strings. `whenToRead` tells agents when to open the group, including when no files in that group have changed.

```yaml
name: Testing
description: Verify behavior with meaningful tests.
whenToRead: When adding or changing behavior, fixing bugs, or reviewing tests.
```

The directory, such as `practices/testing`, supplies the group ID and type. Do not add other fields. YAML metadata must use one document without duplicate keys, anchors, aliases, or explicit tags. For advice on writing useful cues, see [When to read guidance](/reference/rule-authoring/#write-whentoread-guidance-that-helps-selection).

## Rule metadata

Each rule needs YAML frontmatter between `---` lines and a non-blank Markdown body. Here is a complete rule:

```md
---
title: Test changed behavior
whenToRead: When adding or changing externally visible behavior.
impact: HIGH
impactDescription: Prevents behavior changes from silently breaking existing use cases.
tags: testing
---

## Test changed behavior

When a change alters behavior that a caller or user relies on, add or update a test for that outcome.

For example, when a discount changes an order total, assert the resulting total.
Run the relevant tests before considering the change complete.
```

| Field | Requirement |
| --- | --- |
| `title` | Required, non-blank text. |
| `whenToRead` | Required, non-blank text describing when to read this rule. |
| `impact` | Required. Use `CRITICAL`, `HIGH`, `MEDIUM-HIGH`, `MEDIUM`, `LOW-MEDIUM`, or `LOW`. |
| `impactDescription` | Required, non-blank text explaining the consequence the rule addresses. |
| `tags` | Optional non-blank text or an array of unique, non-blank strings. Tags aid search; they do not select rules. |
| `attribution` | Optional list of source credits; see [Rule attribution](#rule-attribution). |

Do not add other frontmatter fields. The group and rule fields named `whenToRead` both guide selection; the body gives the actual instruction and any exceptions. The [authoring rubric](/reference/rule-authoring/) offers writing advice, not extra format requirements. For a step-by-step example, see [Write a rule](/guides/write-rules/).

## Rule attribution

If you adapt someone else's material, you can record its source in the rule:

```yaml
attribution:
  - url: https://github.com/example/rules/blob/0123456789abcdef/source.md
    description: Adapted the error-handling example for this library.
```

Each entry needs an absolute HTTP(S) `url` without credentials and a non-blank `description`. A commit-pinned URL makes the source easier to verify. Attribution does not grant permission to use the material or change the library's license. You may also keep a source credit in the rule body.

## Supporting assets

Keep each rule's obligations and exceptions in its Markdown file. Put longer explanations, images, or sample data in one of these locations:

```text
assets/                                 # Shared by the library
  retry-lifecycle.svg
practices/testing/
  verify-retries.md
  assets/
    verify-retries/                    # Belongs to verify-retries.md
      explanation.md
      example-response.json
```

A rule's asset directory has the same name as its file without `.md`. An asset directory needs its owning rule. Supporting Markdown needs UTF-8 text but no rule frontmatter. Link from a rule with Markdown, for example `[Explanation](assets/verify-retries/explanation.md)`. You may also link to root `assets/` or declared license and notice files.

Local links must point to files in the same rule's assets, shared root assets, declared terms, or the same document. Do not link to another rule or its private assets; move shared material to root `assets/`. Use Markdown links for local files instead of relative `href` or `src` attributes in raw HTML. You may link to external URLs; Code Rules does not download them.

`library check` verifies that local link destinations exist. It rejects symlinks, unsafe paths, and supporting files outside the allowed asset locations. For import limits, see [How imports work](/reference/imports/).

## Library license metadata

Declare one license for the whole library in `rule-library.yaml`. For example:

```yaml
formatVersion: 1
license:
  spdxExpression: MIT
  file: LICENSE.md
  notices:
    - NOTICE.md
```

| Field | Requirement |
| --- | --- |
| `license.file` | Required when `license` is present. Path to the license text, relative to the library root. |
| `license.notices` | Required when `license` is present. Array of notice paths; use `[]` when there are none. |
| `license.spdxExpression` | Optional SPDX expression, such as `MIT`, or a `LicenseRef-` identifier for custom terms. |

Declared files must exist in the library. Code Rules retains them when a project imports the library and links generated rules to them. Rule- and group-level license fields are unsupported. Code Rules validates the declaration's format; it cannot decide whether you own the material or have permission to share it. For publishing guidance, see [License a library](/guides/license-rules/).
