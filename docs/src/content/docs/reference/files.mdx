Every repository that uses Code Rules, whether a project, a library, or both, has the same **Code Rules directory**, `.code-rules/` at its root. It holds the configuration, the rules, skills, and assets the repository authors, vendor snapshots of what it takes from each source, and generated guidance. When the repository installs skills, Code Rules also writes them into **target folders** outside that directory, where agents look for skills.

`.claude/skills/` and `.agents/skills/` exist only for the [skill targets](/reference/configuration/#skill-targets) the repository configures, and only once it installs a skill. Your `AGENTS.md` stays outside the Code Rules directory, at the repository root. A library also has `changes/` in its Code Rules directory, for its [change notes](/reference/rule-versions/#change-notes); see [Library format](/reference/library-format/).

Initialize from the repository root. In Git repositories, other commands find the nearest Git root and use its `.code-rules/` directory. Outside Git, run commands from the repository root. See [Working directories](/reference/cli/#working-directories).

## Authored, vendored, and generated content

The Code Rules directory holds three kinds of content:

- **Authored content: `rules/`, `skills/`, and `assets/`.** The rules, group metadata, skills, and shared assets written in this repository. Add your own rules and skills here, including replacements and forks of rules and skills you include from sources. You maintain these files; sync preserves them. A library publishes exactly this content.
- **Vendor snapshots: `vendor/<source-name>/`.** A copy of what the repository takes from each source, at its recorded library release or commit, with `_source.json`, the record of that revision and of every rule's and skill's version. A library's snapshot mirrors its Code Rules directory, with its `config.yaml` for the manifest. A non-library source's files keep their paths in its repository. Skills a library [borrows](/reference/configuration/#borrowed-skills) are stored with the library that listed them, under `borrowed/<borrowed-source>/`. Snapshots are kept per source because two sources can both have the same group ID. Do not customize them; put your changes in authored content instead.
- **Generated guidance: `generated/`.** The resolved rules your agents read. Code Rules combines the included and authored rules according to `config.yaml`, applies exclusions and replacements, and writes the reading indexes, including `SKILLS.md`. Do not edit this directory; rebuild it after changing your inputs.

Installed skills are output too: Code Rules writes a copy of each installed skill into every target folder, such as `.claude/skills/build-feature/`, from its vendored or authored source. See [Installed skills](#installed-skills).

Think of authored content and `vendor/` as inputs, and `generated/` and the installed skills as the output for your agents.
For example, when you replace a library rule, its vendored copy stays in `vendor/`, your replacement lives in `rules/`, and `generated/` presents the replacement to your agent.

## What to edit

| File or directory | Who maintains it | Purpose |
| --- | --- | --- |
| `AGENTS.md` | You | Tell your agent to read the generated rules. |
| `.code-rules/config.yaml` | You | Choose sources, the rules and skills to include, versions, skill targets, exceptions, and, for a library, its manifest. |
| `.code-rules/rules/`, `skills/`, and `assets/` | You | Add authored rules, group metadata, replacements, skills, and shared assets. |
| `.code-rules/README.md` | `code-rules project init`, `code-rules project build`, and `code-rules project sync` | Explain the repository's rule setup and commands. |
| `.code-rules/vendor/` | `code-rules project sync` and `code-rules project update` | Store vendor snapshots and their records of each rule's and skill's version. |
| `.code-rules/generated/` | `code-rules project sync`, `code-rules project update`, and `code-rules project build` | Provide resolved rules, indexes, and the record of installed skills. |
| Skill folders that Code Rules installed in `.claude/skills/` and `.agents/skills/` | `code-rules project sync`, `code-rules project update`, and `code-rules project build` | Provide installed copies of skills where agents look for them. |
| Other folders in `.claude/skills/` and `.agents/skills/` | You, or the tool that installed them | Code Rules never changes or removes them. |

Keep your changes in configuration and authored content. Edits in `vendor/`, `generated/`, or an installed skill folder will be replaced or removed. To change a skill you include from a source, [fork it](/reference/cli/#fork-a-skill) into `skills/`.
Commit configuration, authored content, both managed directories, and the installed skill folders, so your team, CI, and every fresh checkout use the same rules and skills offline.
Commit the project instructions and README as well.
If your `.gitignore` excludes a target folder, such as with `/.claude/`, change the line to `/.claude/*` and add the exception `!/.claude/skills/`, or `code-rules project check` reports the missing folders. Git can't re-include a folder inside an excluded folder, so `!/.claude/skills/` alone doesn't work after `/.claude/`.

Use `code-rules project build` to regenerate guidance from stored inputs, and `code-rules project check` to verify consistency without changing files.
Missing or mismatched vendor snapshots require `code-rules project sync`.
For recovery and file ownership details, see [Sync and recovery](/reference/sync/).

Generated Markdown and the managed Code Rules guide include a "Generated by Code Rules" notice and regeneration instructions. `generated/provenance.json` and `generated/installed-skills.json` store that notice in `generatedNotice`. Copied license and notice files retain their original bytes. An installed `SKILL.md` carries a [marker line](#installed-skills) instead, because its frontmatter must start at the first byte.

## Project and group guides

`code-rules project init` creates `.code-rules/README.md` with definitions and commands for managing rules. It preserves the repository's own `README.md` at the repository root.

After upgrading Code Rules, run `code-rules project build` to refresh an older guide and regenerate guidance, or rerun `code-rules project init` to refresh only the guide and setup files. Build, sync, and init preserve valid configuration and authored content but refuse to overwrite a manually edited guide. Preserve those notes separately before refreshing it. `code-rules project check` reports a missing or outdated managed guide without changing it.

Managed guide format changes are breaking changes under the [version policy](https://github.com/fabricahq/code-rules/blob/main/.release-planner/policy.md#choosing-a-version): a new minor version of Code Rules before 1.0, and a new major version after 1.0. This guide is separate from your repository's own README.

Group creation also writes a `README.md` beside `_group.yaml`. Group guides explain how to add, edit, and validate rules. These are authoring documents, excluded from rule loading and generated guidance. Existing group files are preserved.

## Where agents start

Point your agent to `.code-rules/generated/RULES.md`. It lists the groups and explains when to read each one.
Agents then open relevant groups and read the applicable rules in full.
When the repository installs skills, `RULES.md` also has one line pointing to `SKILLS.md`, so the same instructions reach agents whose tools don't load skills from the target folders.
See [Plan, write, and review](/for-agents/) for instructions you can add to `AGENTS.md`.

| Generated path | Contents |
| --- | --- |
| `RULES.md` | The entry point for discovering relevant groups. |
| `SKILLS.md` | One entry per installed skill. Present only when the repository includes skills. |
| `groups/` | Group pages containing full rules or summaries with links to full definitions. |
| `rules/` | Individual resolved rules, available even when a group also includes them inline, and the reference-only rules that installed skills cite. |
| `libraries/` | Source summaries and retained license and notice files. |
| `installed-skills.json` | The skill folders Code Rules installed in the target folders. Present only when the repository includes skills. |
| `provenance.json` | Machine-readable source versions, origins, and replacement decisions. |

Large indexes can span multiple pages. Follow the page directory and navigation links before selecting rules, and complete any truncated reads.
Full rule definitions are never shortened to fit an index.

A rule's source name appears in its generated path. For example, `fabrica:practices/testing/test-failure-paths` lives at `rules/fabrica/practices/testing/test-failure-paths.md` under `generated/`.
Authored rules and replacements have no source name, so `practices/testing/test-failure-paths` lives at `rules/practices/testing/test-failure-paths.md`. Excluded rules and replaced rule bodies have no generated rule file.
A rule that only an installed skill cites has a generated rule file at the same kind of path, but no group page or `RULES.md` entry lists it.

For rule versions, replacement history, and retained license records, see [Provenance](/reference/provenance/).

## Installed skills

For each installed skill, Code Rules writes the folder `<target>/<install-name>/` in every [skill target](/reference/configuration/#skill-targets), such as `.claude/skills/build-feature/`. The folder holds every file of the skill as its source has it, with each file's executable bit, plus two changes to `SKILL.md`, and a third when the repository [renames](/reference/configuration/#rename-a-skill) the skill: its `name` field becomes the install name.

First, a marker comment is the first line after the frontmatter:

```markdown
---
name: build-feature
description: Build a feature from an agreed spec, one slice at a time. Use when starting implementation of a new feature or a change to an existing one.
metadata:
  syllabus-skill-type: playbook
  syllabus-rules-used: |
    practices/testing/test-behavior-not-implementation
    practices/verification/verify-on-the-surface-users-touch
  syllabus-skills-used: |
    skills/tdd
---
<!-- code-rules:installed fabrica:skills/build-feature 1.3.0. Do not edit; fork it with code-rules project add skill --from. -->

1. Read the spec and name the slice you're building.
```

The marker names the skill's project ID and its version. A skill from a non-library source shows its full commit SHA in place of a version. An authored skill has no version, and its marker says where to edit it instead: `<!-- code-rules:installed skills/fix-bug. Do not edit; edit .code-rules/skills/fix-bug/ instead. -->`. A `SKILL.md` without frontmatter, which only a non-library source can supply, gets the marker as its first line. The marker never includes the Code Rules version, so upgrading Code Rules doesn't change installed copies.

Second, a generated section is appended to the end of `SKILL.md`. When the skill cites rules, it lists each one's project ID, version, and generated rule file:

```markdown
## Rules this skill applies

Read each rule in full before the step that applies it.

- `fabrica:practices/testing/test-behavior-not-implementation` 2.0.0: [.code-rules/generated/rules/fabrica/practices/testing/test-behavior-not-implementation.md](../../../.code-rules/generated/rules/fabrica/practices/testing/test-behavior-not-implementation.md)
- `practices/verification/verify-in-staging`, which replaces `fabrica:practices/verification/verify-on-the-surface-users-touch`: [.code-rules/generated/rules/practices/verification/verify-in-staging.md](../../../.code-rules/generated/rules/practices/verification/verify-in-staging.md)

Skills this skill uses: `tdd`
```

- A rule the repository replaced shows the replacement, its version when it has one, and the rule it replaces.
- A rule the repository excluded without a replacement shows "excluded by this project" and the exclusion's reason, with no link.
- The "Skills this skill uses" line names each skill it calls by its install name, including those your configuration's [`skills.uses`](/reference/configuration/#declare-the-skills-a-skill-calls) adds, and those an authored skill replaces. It appears only when the skill calls others, and without a heading when the skill cites no rules.

Links are relative to the installed `SKILL.md`, so they work from either target. A skill that cites no rules and calls no skills gets no generated section.

Code Rules records what it installed in `generated/installed-skills.json`:

```json
{
  "formatVersion": 1,
  "generatedNotice": "Generated by Code Rules. …",
  "skills": [
    {
      "name": "build-feature",
      "id": "fabrica:skills/build-feature",
      "version": "1.3.0",
      "commit": null,
      "targets": [
        ".agents/skills/build-feature",
        ".claude/skills/build-feature"
      ],
      "digest": "8c2f…d41a"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `formatVersion` | The record's format version, `1`. |
| `name` | The install name, which is the installed folder's name. |
| `id` | The skill's project ID. |
| `version` | The installed version, or `null` for an authored skill, a skill from a non-library source, or one with unreleased changes. |
| `commit` | For a skill from a non-library source, including a borrowed one, the full commit SHA it came from; otherwise `null`. |
| `targets` | Each folder Code Rules installed the skill in, relative to the repository root, sorted. When one target folder links to the other, both paths are listed, though the files are written once. Empty when the repository has no skill targets. |
| `digest` | The SHA-256 checksum of the installed folder: every file's path, executable bit, and contents, as sync wrote them. |

This record is how Code Rules knows which folders it owns: it replaces and removes only the folders listed here, and refuses to write over any other. See [Who owns the target folders](/reference/sync/#who-owns-the-target-folders).

### SKILLS.md: find a skill

`generated/SKILLS.md` has one entry per installed skill, so people, and agents whose tools don't load skills from the target folders, can see what's installed, where it came from, and why:

```md
### build-feature

Build a feature from an agreed spec, one slice at a time. Use when starting implementation of a new feature or a change to an existing one.

- **Skill:** `fabrica:skills/build-feature`, version 1.3.0
- **Level:** recommended by `fabrica`, release 7
- **Type:** playbook
- **Installed at:** `.agents/skills/build-feature/SKILL.md`, `.claude/skills/build-feature/SKILL.md`
- **Applies:** 2 rules
- **Uses:** `tdd`
- **Installed because:** included
```

**Level** names the skill's [level](/reference/configuration/#skill-levels) and the library and library release that set it, such as `required by fabrica, release 7`. It's absent for an authored skill, and for one the repository named directly from a non-library source. A skill installed only because another one calls it says so, such as `**Installed because:** used by build-feature`. **Type** is absent for a skill without one, and **Uses** for a skill that calls none. A renamed skill's heading is its install name, and its entry adds `**Renamed from:** review-change`. A skill from a non-library source shows its commit in place of a version. With no skill targets, **Installed at** gives the skill's source folder in `vendor/` or `skills/` instead, and **Applies** lists the generated file of each rule it cites, because no installed copy carries that list.

`SKILLS.md` lists skills; it doesn't tell agents to prefer them over skills a person installed. See [Personal skills with the same name](/reference/sync/#personal-skills-with-the-same-name).

`RULES.md` points to this file with one line:

```md
This project also installs agent skills. See [SKILLS.md](SKILLS.md) for what each one does and where it's installed.
```

## Example: follow a rule from the index

These abbreviated excerpts show how an agent finds an authored rule. The full generated files also include reading instructions, metadata, and source information.

### RULES.md: choose a group

`.code-rules/generated/RULES.md` is the starting point. Each entry tells the agent when to open a group:

```md
### Testing

**When to read this group:** When adding or changing behavior, fixing bugs, or reviewing tests.

**Open group:** [Testing](groups/practices/testing.md)
```

### Group page: find the rules

`.code-rules/generated/groups/practices/testing.md` contains the group's rules. Small groups include full rule text; larger groups use summaries like this, linking to each full definition:

```md
### Test changed behavior

Rule ID: `practices/testing/test-changed-behavior`

**When to read:** When adding or changing externally visible behavior.

**Read full rule:** [Test changed behavior](../../rules/practices/testing/test-changed-behavior.md)
```

A rule from a source also shows its version below its ID, so agents and reviewers can cite it:

```md
Rule ID: `fabrica:practices/testing/verify-retry-limits`

Version: 1.3.0
```

Authored rules have no version.

### Rule file: read the guidance

`.code-rules/generated/rules/practices/testing/test-changed-behavior.md` contains the rule the agent follows:

```md
# Test changed behavior

Rule ID: `practices/testing/test-changed-behavior`

## Guidance

When a change alters behavior that a caller or user relies on, add or update a test for that outcome.
```

The authored version stays in `.code-rules/rules/practices/testing/test-changed-behavior.md`. Edit that source file and rebuild to update the generated copy.
