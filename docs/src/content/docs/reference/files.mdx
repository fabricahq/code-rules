`rule-library.json` declares the library format:

```json
{ "formatVersion": 1, "license": { "expression": "MIT", "file": "LICENSE.md", "notices": [] } }
```

Discover groups only under `techs/` and `practices/`.
Misplaced rule files should fail validation rather than disappear from imports.

## Library license metadata

The optional `license` object declares the library's default terms:

| Field | Meaning |
| --- | --- |
| `license.expression` | Declared SPDX expression, such as `MIT` or `MIT OR Apache-2.0`, or a `LicenseRef-…` for custom terms. Optional for compatibility with existing manifests. |
| `license.file` | Path to the actual license text, relative to the library root. |
| `license.notices` | Paths to accompanying notices, relative to the library root; use an empty array when none apply. |

When `license` is present, `file` and `notices` are required and all declared files must exist within the library.
The planned import and workspace workflow preserves these files from the resolved source commit and includes them in snapshot digests.
The offline builder accepts supplied snapshots, verifies that declared files exist, and links generated guidance to those retained files. It does not fetch files or compute workspace snapshot digests.
If the declaration is absent, provenance records an empty `licenses` array. A legacy declaration with files but no expression records `expression: null`; that differs from no declared terms. Code Rules never infers an identifier from a filename. It checks that supplied expressions are non-blank single-line strings, but does not certify SPDX identifier validity, ownership, or agreement between the label and the license text.

One library-wide license declaration covers every group and rule. Rule- and group-level `license` or `licenses` fields are rejected.
Keep original attribution with each rule and include required notices in the library manifest. Material requiring a different declaration belongs in a separate library.
See [License rules](/guides/license-rules/) for publisher guidance and the boundary with the consuming project's license.

## Group metadata

Library authors define each group's selection guidance in its `_group.json`, before the group is imported.
Builds reads that source metadata and renders its `whenToRead` cues in the generated root index; it does not infer them from the current rules.
Use the existing `whenToRead` field for this guidance rather than adding a separate `whenToUse` field.

```json
{
  "name": "Testing",
  "description": "Verify behavior with meaningful tests.",
  "whenToRead": [
    "Adding or changing behavior, even when no test files are in the diff.",
    "Fixing a bug or modifying tests."
  ]
}
```

The directory supplies the group's ID and type.
The generated index includes its name and when-to-read guidance. The description remains in the source metadata.
Follow the shared [whenToRead authoring guidance](/reference/rule-authoring/#write-whentoread-guidance-that-helps-selection) when filling in the group's reading cues.

## Rule metadata

Each rule requires `title`, `whenToRead`, `impact`, and `impactDescription` frontmatter, followed by its Markdown body.
`tags` is optional: use a non-blank string of comma-separated topics or an array of unique, non-blank strings. An empty array is also accepted.
Tags provide search terms, such as `testing` on a Go rule. Builds preserves supplied tags but does not use them for selection, grouping, or enforcement. Use `whenToRead` to describe applicability.
Use the existing impact vocabulary: `CRITICAL`, `HIGH`, `MEDIUM-HIGH`, `MEDIUM`, `LOW-MEDIUM`, or `LOW`.
Impact describes the significance of the consequence a rule helps prevent.
Follow the canonical [impact authoring guidance](/reference/rule-authoring/#describe-impact-through-consequences) for level definitions and examples.
Agents select rules using `whenToRead`, follow the full guidance and exceptions, and assess finding severity from concrete evidence.
All applicable rules matter regardless of impact.

`whenToRead` is a required non-empty string describing work that should trigger reading, including before code exists.
The group field of the same name remains an array of group-selection cues.
The full body defines obligations, implementation guidance, exceptions, and validation guidance.
Existing snapshots and local replacements must add rule-level `whenToRead` before building with this format.

See [Make a rule](/guides/write-rules/) for a complete example.

## Rule attribution

A rule may record the source of an adaptation independently of the library's license:

```yaml
attribution:
  - url: https://github.com/sindresorhus/eslint-plugin-unicorn/blob/5d9d745c5365b6fdb824db1122ff982dd824b11a/docs/rules/no-for-each.md
    description: Adapted from Sindre Sorhus's ESLint Unicorn rule; added task guidance.
```

Each optional `attribution` entry requires an absolute HTTP(S) `url` without credentials and a non-blank `description`.
Use a commit-pinned URL and describe the adaptation. These citations identify source material; they do not override the library license.
Existing attribution in prose or other metadata remains preserved.

## Attribution

Keep source attribution with the rule, in its metadata or Markdown body.
Imports preserves attribution in vendored sources; Builds preserves it in each individual generated rule file.
A separate attribution file is not required by the format.

When a library includes applicable library-level license or notice files, preserve those files with its vendored snapshot.
Keep references to them valid after import.

## Generated index and rules

`generated/RULES.md` introduces the project's declared practices and explains how to select technology and practice groups.
Each entry contains a group name, **When to read** guidance, and an explicit **Open group** link.
When multiple sources contribute to a group, their reading cues remain separate and labeled by source.
One instruction above the entries directs the agent to open relevant group indexes and read applicable rules in full.
It links to `provenance.json` for source versions and rule origins.

`generated/groups/` contains group discovery pages; `generated/rules/` contains individual effective definitions.
Each folder includes a short `README.md` explaining its contents and pointing back to `generated/RULES.md`, the primary entry point. These descriptions do not add a required reading step.
Group IDs such as `practices/testing` remain unchanged. The corresponding page lives at `groups/practices/testing.md` relative to `generated/`.

Each group page, such as `generated/groups/practices/testing.md`, states whether it contains full rules or summaries only.
A small group includes every active rule's complete effective definition inline.
A larger group lists each active rule's source-qualified ID, plain title, **When to read**, **Impact**, **Why it matters**, and an explicit **Read full rule** link.
Reading instructions appear first; navigation, provenance, and regeneration instructions appear at the bottom.
Read every relevant or plausibly relevant rule completely before planning, implementation, validation, or diagnosis.
Selection alone establishes neither compliance nor a violation; impact supplies consequence context rather than automatic finding severity.

`BuildInput.groupInlineMaxBytes` defaults to 8 KiB and accepts non-negative safe integers; zero forces summaries.
The complete rendered group page must fit both this limit and `indexMaxBytes` to include full rules inline.
The measurement counts UTF-8 bytes, including instructions, metadata, examples, attribution, and the footer.
Rule count and line count do not determine the format. A single large rule can require a summary index.
This is a provisional delivery default, not an empirically validated threshold for agent compliance.

Full definitions live under `generated/rules/<source-name>/<rule-path>.md`.
For example, `fabrica:techs/typescript/prefer-type-aliases` maps to `rules/fabrica/techs/typescript/prefer-type-aliases.md`.
The source name is a directory so generated paths are portable; the ID retains its colon.
A replacement retains that path and ID while supplying its local title, applicability, and full body.
Excluded rules and superseded bodies have no generated rule file.
Source links, attribution, library license links, and replacement provenance remain with the effective definition in both formats.
Individual rule files remain available at stable paths even when the group includes full rules.
Both copies come from the same resolved definition. Relative links are relocated from the actual output directory.
Inline rules nest their headings and namespace Markdown reference labels.
Same-file fragment links in inline rules point to the standalone definition, avoiding ambiguity between repeated headings across rules.

Indexes use stable ordering and a configurable UTF-8 byte budget (`BuildInput.indexMaxBytes`, default 24 KiB in the offline API).
An oversized index becomes a directory listing every numbered sibling part, such as `testing.part-1.md`.
Each part contains complete entries and a link back to the directory; inspect all parts before selecting rules.
The root group index uses the same mechanism when necessary.
If one entry or the complete part directory cannot fit, building fails with an actionable error instead of omitting entries.
Full rule bodies are never shortened to fit an index budget. Complete any truncated reads of those files.
This budget is a delivery setting, not a measured model-compliance threshold.

Builds returns the complete generated file set. The planned Workspace subsystem must replace obsolete output, including old parts, removed rule files, and the former top-level `techs/` and `practices/` group pages, when installing it.
Exclusions and replacement reasons remain in project configuration; provenance records active origins and replacement reasons.
The consuming repository's root license is not rewritten.

## Provenance records

Each proposed `vendor/<source-name>/_source.json` records the source name, repository, requested `ref`, full `resolvedCommit`, `groupSelection`, concrete imported `groups`, and file digests.
`groupSelection` is the configured list or selector (`"*"`, `"practices/*"`, or `"techs/*"`). Pattern snapshots must record the exact selector and supply every group within its scope at that revision.
Legacy snapshots without this field imply the explicit `groups` list; they cannot satisfy a wildcard selection.
Offline commands verify that the recorded repository, ref, and groups match configuration and that file digests match the snapshot.
For a commit-valued ref, the resolved commit must equal that SHA.
For a tag, offline checks use the recorded commit and do not verify the tag's current remote target.

`generated/provenance.json` records the tool version, every named source with its requested ref and resolved commit, and active rule origins.
Each source records `groupSelection` alongside the expanded `groups` list, keeping the adoption intent and actual included groups visible.
A replacement retains both its targeted source-qualified ID and the local definition's origin.
Generated output excludes changing timestamps and machine-specific paths.

These metadata files support repeatability and diagnosis.
They do not independently authenticate a locally modified snapshot against its remote repository.


### License declarations in provenance

Source records include `licenses` with library-relative paths and retain `licenseFiles` for compatibility. The array contains the single library declaration, or is empty when licensing is undeclared.
Each active imported rule records that same declaration, its `attribution`, and `licenseBasis: "library"`. Its license paths start with `vendor/<source>/` and resolve from the configuration directory, above `generated/`.
Local additions and original local replacements have no imported library license: their `licenses` array is empty and `licenseBasis` is `undeclared`. An upstream rule ID does not assign the upstream license to a local replacement. Its source library's declaration remains in the source record.

For example, the licensed-library walkthrough produces:

```json
{
  "licenseBasis": "library",
  "licenses": [{
    "expression": "MIT",
    "files": ["vendor/licensed/LICENSE.md"],
    "attributionFiles": ["vendor/licensed/NOTICE.md"]
  }],
  "attribution": [{
    "url": "https://github.com/sindresorhus/eslint-plugin-unicorn/blob/5d9d745c5365b6fdb824db1122ff982dd824b11a/docs/rules/no-for-each.md",
    "description": "Adapted from Sindre Sorhus's ESLint Unicorn rule; added task guidance."
  }]
}
```

These are preserved declarations, not a legal verification status. `licenseBasis: "undeclared"` means no applicable terms were declared to Code Rules; it does not mean public domain or permission to redistribute.
