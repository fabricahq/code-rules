A **library** is an independently maintained collection of rule **groups** and **skills**. Libraries are useful because projects import them: you write rules and skills once and reuse them in every codebase that needs them. A **project** is a codebase that uses **rules** to guide its agents, and can install skills for them. It can write its own rules and skills, import them from libraries, or both.

Libraries live in Git repositories. This page covers what makes a repository a library. For the rule and group files inside it, see [Rule and group format](/reference/rule-format/); for skill folders, see [Skill format](/reference/skill-format/). For how each rule and skill is versioned, see [Rule and skill versions](/reference/rule-versions/).

The library root holds three kinds of things:

- **Rule groups** under `techs/` and `practices/`, each with its group metadata and rules.
- **Skills** under `skills/`, one folder per skill.
- **Library-wide files**: `rule-library.yaml`, group metadata, shared files in `assets/`, the declared license and notice files, and presets in `presets/`.

`rule-library.yaml` is the library's manifest. It declares the library format and its [license](#license-metadata):

```yaml
formatVersion: 1
license:
  spdxExpression: MIT
  file: LICENSE.md
  notices: []
```

Code Rules discovers groups only under `techs/` and `practices/`, and skills only as `skills/<name>/SKILL.md`.
Within selected groups, Markdown files outside reserved asset directories are rules. The group-root `README.md` and declared license and notice files, which can't use a rule's path, are exempt. Group READMEs are authoring documentation, not generated rule guidance.
[Change notes](/reference/rule-versions/#change-notes), which record how rules and skills changed, live in the library-root `changes/` directory. Projects never import them.
Library releases are Git tags, not files; see [Library releases](/reference/rule-versions/#library-releases).
Other supporting files, including `_README.md`, must live in an asset directory.
Rules and [group metadata](/reference/rule-format/#group-metadata) must use valid paths; wildcard discovery also rejects rules whose group metadata is missing.
The builder does not inspect the contents of unselected groups.

`rule-library.yaml`, change notes, group metadata, and presets use one YAML document per file. Duplicate keys, anchors, aliases, and explicit tags are rejected. Generated snapshot and provenance files remain JSON.

## Skills

Each folder in the library-root `skills/` directory is one skill, and its `SKILL.md` names it. A skill's ID is its path without `/SKILL.md`, such as `skills/build-feature`. `skills/` holds only skill folders, each directly inside it. Skills don't belong to groups, so a skill folder is never inside `techs/` or `practices/`, or inside another skill.

`code-rules library check` validates every skill, and a project installs only the skills it selects, plus the skills they use. A skill's version covers its whole folder; see [What a version covers](/reference/rule-versions/#what-a-version-covers). For the folder's contents, the `SKILL.md` fields, and every check, see [Skill format](/reference/skill-format/).

A skill can cite rules from any group in the library with `cr-rules-used`, and a project that installs it imports those rules too. Rules can't link to skills, and skills can't link to rules or other library files: a skill cites rules by ID, and its links stay inside its own folder.

## Shared assets

Files that several rules use, such as a shared diagram, live in the library-root `assets/` directory. A rule's own supporting files live beside it instead. [Supporting assets](/reference/rule-format/#supporting-assets) covers both locations and the rules for linking to them.

Shared files are library-wide files: they aren't part of any rule or skill version, need no change note when they change, and reach projects with the next library release, when each project runs `code-rules project update`. See [What a version covers](/reference/rule-versions/#what-a-version-covers).

## License metadata

The optional `license` object declares the library-wide terms. Authors should use root-level `LICENSE.md` and optional `NOTICE.md`; the manifest can identify other source locations:

| Field | Meaning |
| --- | --- |
| `license.spdxExpression` | Declared SPDX expression, such as `MIT` or `MIT OR Apache-2.0`, or a `LicenseRef-…` for custom terms. Optional for compatibility with existing manifests. |
| `license.file` | Path to the actual license text, relative to the library root. |
| `license.notices` | Paths to accompanying notices, relative to the library root; use an empty array when none apply. |

When `license` is present, `file` and `notices` are required and all declared files must exist within the library.
Declared license and notice files are [library-wide files](/reference/rule-versions/#what-a-version-covers), so they can't be part of a rule's or skill's version: a declared path can't be a rule's Markdown file, lie in an asset directory inside a technology or practice group, such as `practices/testing/assets/verify-retry-limits/LICENSE`, or lie in a skill folder, such as `skills/build-feature/LICENSE`. Otherwise a later library release could replace a file that a project's pinned rule or skill version covers. `code-rules library check` rejects such a declaration, and projects refuse to import a library release whose manifest has one.
Unknown fields in the license declaration are rejected so misspellings cannot silently discard intended metadata.
Code Rules retains the declared files from the resolved source commit and links generated rules to unchanged copies. Offline builds require those files in the stored snapshot.
If the declaration is absent, provenance records `license: null`. A legacy declaration with files but no expression records `spdxExpression: null`; that differs from no declared terms. Code Rules never infers an identifier from a filename. It validates supplied SPDX expressions and identifiers using its bundled license list, while allowing `LicenseRef-` identifiers for custom terms. This validates the declaration format, not ownership, permissions, or agreement between the declaration and the retained text. The former `license.expression` field is rejected with a rename instruction; use `license.spdxExpression`.

Every imported library has a generated `libraries/<source-name>/README.md` with its repository, imported library release, requested `ref` or pins, each rule's and installed skill's version and whether the project excludes or replaces it, or still imports it after the library retired it, a notice when it was imported from unreleased changes, declared SPDX expression when supplied, and links to retained terms and provenance. Libraries without a license declaration omit the `licenses/` directory. [Provenance](/reference/provenance/) documents the machine-readable records.

The manifest paths select **source files**, not output locations. For declared terms, Code Rules uses these fixed destinations:

```text
generated/libraries/<source-name>/licenses/LICENSE.md
generated/libraries/<source-name>/licenses/notices/001.md
generated/libraries/<source-name>/licenses/notices/002.md
```

`<source-name>` is the configured library alias. Unique notice files are numbered in declaration order; repeated paths and a notice path identical to the license path are copied only once. No notice files are generated when none are declared. Contents, including whitespace and line endings, are preserved. Output paths are not configurable. Vendored snapshots retain the original names for traceability. Declared terms are retained even when exclusions or replacements leave no active rules from that library.

One library-wide license declaration covers every group, rule, and skill. Rule- and group-level `license` or `licenses` fields are rejected. A skill's `SKILL.md` can carry the Agent Skills `license` field, but it's informational: `code-rules library check` warns when it differs from the library's SPDX expression; see [Skill format](/reference/skill-format/#licenses).
Keep original attribution with each rule and include required notices in the library manifest. Material requiring a different declaration belongs in a separate library.
See [License rules](/guides/license-rules/) for publisher guidance and the boundary with the consuming project's license.

## Presets

A **preset** is a starting configuration that a library publishes for projects to extend, such as an organization's default libraries, groups, and skills. Each preset is one file, `presets/<name>.yaml`, at the library root. `<name>` follows the [skill name grammar](/reference/skill-format/#skill-ids): 1 to 64 lowercase letters, digits, and hyphens, without a leading, trailing, or doubled hyphen. A project names it in its `extends` field, such as `preset: team-defaults`.

```yaml
schemaVersion: 2
skillTargets: [claude, agents]
sources:
  fabrica:
    repository: https://github.com/fabricahq/public-rules.git
    groups: [practices/testing, practices/code-review]
    skills: [skills/build-feature, skills/review-pr]
    exclude:
      skills/fix-bug:
        reason: Teams here file bugs through the incident workflow instead.
  team:
    repository: https://github.com/example/engineering-rules.git
    groups: "*"
    skills: "*"
```

A preset uses the same shape as [project configuration](/reference/configuration/), with these fields only:

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Required. `2`. |
| `skillTargets` | Optional. The install targets for projects that extend the preset and don't set their own. |
| `sources` | Required. Map of source names to library or plain repository configurations, with the same fields a project's sources accept: `repository`, `groups`, `rules`, `skills`, `exclude`, `pins`, `ref`, `follow`, `skillsRoot`, and `skillUses`. |

A preset has no `extends`: a preset can't extend another. It can't refer to a project's local files, so its exclusions take a `reason` but no `replacedBy` or `basedOn`. Unknown fields are rejected, and duplicate keys, anchors, aliases, and explicit tags are rejected as in other YAML files. A preset can list the library it belongs to as one of its sources, by the library's repository address.

`code-rules library check` validates each preset's syntax and fields. It doesn't contact the repositories a preset names, so a selection that a source doesn't offer, such as a misspelled skill ID, fails when a project that extends the preset syncs.

Presets are library-wide files. They have no versions and need no change notes; a project gets each preset as it was in one library release, and `code-rules project update` moves it to the newest library release. A preset only selects: every rule and skill it selects still comes from its own source, with that source's versions, credit, and license. For how a project extends a preset and how its configuration merges with the project's, see [Extend a preset](/reference/configuration/#extend-a-preset) and [Share defaults with presets](/guides/presets/). A project that names a preset its library doesn't publish fails to sync with `preset-not-found`.

## Read libraries from other tools

Tools written in Go, such as a catalog of libraries, can read library release tags, release records, rule files, group metadata, and the [canonical group list](/concepts/groups/#canonical-group-ids) with the `github.com/fabricahq/code-rules/coderules` package, whose Go documentation describes its API. Code Rules reads libraries through the same package, so both read them the same way. The package only parses text the tool has already read, such as with a Git library; it has no Git, filesystem, or network access. It follows Code Rules' version, and its API may change before Code Rules 1.0.0.
