# Walk through rule applicability indexes

Explore the Builds deliverable in [PR #3](https://github.com/fabricahq/code-rules/pull/3) through one retry-client example. Allow about 10 minutes. Each button runs the real builder with illustrative library data.

You will follow the same path an agent follows: **choose groups, scan rule applicability, then read the full rules**. You can repeat the chapters independently. Results appear in the **Files** panel, with a separate folder for each experiment.

Before writing code, TypeScript, testing, and code-design rules all matter. A rule whose trigger only describes an existing defect would be easy to miss at this stage.

During review, a change from three attempts to five makes the testing rule relevant even if no test file changed. Read the full replacement to establish the actual requirement. Reading a design rule, or counting helpers, does not establish a design violation. Impact describes the consequence the rule addresses. Follow every applicable rule regardless of impact, and assign finding severity from concrete evidence and consequences.

## 4. Author a discoverable rule

<Command
  id="inspect-authoring"
  command="bun tests/manual/applicability-walkthrough.ts authoring"
  title="Open the shared rubric and example rule"
  successMessage="Open the two files under 04-authoring."
/>

The canonical authoring document supplies one flexible template for technology and practice rules. The example uses a broad activity trigger and a precise obligation:

Group cues describe the area of work. Code design covers code organization, responsibility boundaries, and interactions between functions and modules, even with only one rule today.
The individual retry-stage rule has a narrower reading cue about coordinating request execution, retry decisions, and final results.

| Question | Where the answer belongs |
| --- | --- |
| Is this relevant before I write code, or during review? | Required `whenToRead` metadata. For example: when planning, writing, changing, or reviewing an operation that coordinates several steps. |
| Why does it matter? | `impact` and `impactDescription` describe credible consequences. They do not determine applicability or finding severity. |
| How do I implement it? | Useful choices, steps, and examples in the body. A separate Implementation heading is optional. |
| What would demonstrate compliance or a violation? | Observable evidence and boundaries in the body. A separate Validation heading is optional. |

For the retry-stage rule, understandable inline steps can comply. Extracting helpers merely to shorten a function is not the requirement. Authors should consider implementation and validation separately, while avoiding sections that repeat what the obligation already says.

Open `name-retry-stages.md` to compare its three parts: `whenToRead` triggers reading before code exists; Implementation explains when to extract details; Validation identifies evidence and exceptions.

The definition's effective origin is local because the original repository does not use the Code Rules format. Its `licenses` entry explicitly names `MIT`, points to the complete retained license and notice, and its `attribution` identifies the original document at a pinned commit. The generated rule displays these declarations after its guidance. The fixture runs offline and does not fetch or run ESLint Unicorn.

For a compatible imported library, rules without their own declarations inherit the library's declared default. A local replacement supplies its own applicable terms; retaining the upstream rule ID does not automatically assign the upstream license. Code Rules preserves declarations rather than certifying permissions.

For the full authoring workflow, read `docs/src/content/docs/guides/adapt-rules.md` in the checkout. It walks through choosing a source revision, drafting a local or shared adaptation, retaining terms, inspecting generated provenance, and reviewing later upstream changes.

The planned library commands are `code-rules library init`, `code-rules library add group <group-id>`, `code-rules library add rule <rule-id>`, and `code-rules library check`. They are not implemented; this runbook exercises the working offline generator. The proposed setup flow is in `docs/src/content/docs/guides/create-library.md`.

This example packages the same adaptation as a compatible library. The manifest declares MIT once; the rule has no `licenses` field of its own.

The library repository and revision are illustrative fixture data, not a fetched upstream library. The retained ESLint Unicorn license and attribution are real.

| Open | What to notice |
| --- | --- |
| `config.json` | The consuming project selects the `licensed` library with `groups: "*"`. |

## 8. Review the result

You have inspected real output for group discovery, rule selection, replacements, exclusions, local additions, bounded index pages, and authoring guidance.

The walkthrough's assertions establish file behavior. The implementation and review chapters explain how an agent should use those files; they do not prove that an agent will select every relevant rule or comply with it.

The complete repository gate is `bun run check`. The focused walkthrough test is `runbooks test tests/manual/runbooks/applicability-index`. Imports fetching, workspace installation and stale-file removal, the CLI, and private-library migration remain separate work.
