Code Rules v0.2.0 gives every rule its own version. Library authors record each change with a short note and publish it in a library release. Projects preview new rule versions, adopt them when they're ready, pin the rules they want to hold back, and fork rules they need to change.

**This release has breaking changes.** Projects that import libraries must update `.code-rules/config.yaml` and import them again, and a library must publish a `release/<number>` tag before projects can follow its rule versions. See Breaking Changes below for the steps.

## ✨ New Features

### Per-rule versions

Each rule in a library now has its own [semantic version](https://code-rules.fabricahq.com/guides/version-rules/#semantic-versions), starting at `1.0.0`. The version describes how the rule's obligation changed: major when work that complied before could now fail, minor when the rule adds guidance, and patch when it only clarifies. Generated guidance shows each imported rule's version, so agents and reviewers can cite the exact version they followed. See [Version your rules](https://code-rules.fabricahq.com/guides/version-rules/). (#71, #76)

### Change notes

Library authors record each rule change with `code-rules library change`. It writes a small note in `changes/` with the size of the change and a one-line summary for the projects that update:

```sh
code-rules library change practices/testing/verify-retry-limits \
  --bump minor \
  --summary 'Add a Python example of the retry-limit test.'
```

Each note is its own file, so pull requests that change the same rule never conflict. Use `--retire`, with `--replaced-by` when a better rule replaces it, to retire a rule. (#71, #73)

### Library releases

`code-rules library release` publishes every pending change note at once as a library release: an annotated `release/<number>` tag that records every rule's version, and, for libraries on GitHub.com, a GitHub Release page with generated release notes. Preview it first with `code-rules library release --dry-run`:

```sh
code-rules library release --dry-run
code-rules library release
```

The command refuses unless you're on the remote's default branch, your branch matches the remote exactly, and `code-rules library check` passes. The GitHub Release page needs the GitHub CLI, `gh`, installed and signed in; skip it with `code-rules library release --no-github-release`. If a run stops after pushing the tag, run it again to finish. See [Publish a library release](https://code-rules.fabricahq.com/guides/version-rules/#publish-a-library-release). (#71, #75)

### Review and adopt updates with `code-rules project update`

`code-rules project update` previews every newer rule version, new rule, and retirement with the author's summaries, then applies exactly what it showed after you confirm. Without a terminal it only previews, so pass `--yes` to apply in scripts and CI.

```text
team
  major     practices/testing/verify-retry-limits  1.3.0 -> 2.0.0
            Require a test at the limit for every retry policy.
  new       practices/testing/verify-retries       1.0.0
            Add the rule.
  pinned    practices/testing/verify-backoff       1.3.0
            Newest version: 2.0.0.
            Reason: Waiting on the author's response to acme/.code-rules#45.
```

- Update one library with `code-rules project update team`, or one rule with `code-rules project update team:RULE`.
- Pin a rule to an exact version, with a reason, under the source's `pins` in `.code-rules/config.yaml`, or with `code-rules project update --keep SOURCE:RULE --reason '...'`. Updates never move a pinned rule.
- Decline a new rule with `code-rules project update --exclude SOURCE:RULE --reason '...'`.
- Replace a forked rule with a fork of the library's newest version with `code-rules project update --update-fork SOURCE:RULE`. This overwrites your edits to the fork.

See [Update rules](https://code-rules.fabricahq.com/guides/update/). (#71, #77, #83)

### Fork a library rule

`code-rules project add rule ID --from LIBRARY@VERSION` copies one version of a library rule and its assets into `local/`, so your project controls its text. It adds attribution and an exclusion that records the forked version as `basedOn`. `code-rules project update` then lists the library's later changes to the rule, so you can decide whether your fork needs them. (#71, #78)

### Change note checks for libraries

After a library's first library release, `code-rules library check` fails when a changed, new, or deleted rule has no change note, or a note doesn't match a change. When it passes, it previews the versions the next library release will publish. `code-rules library init` now also writes `.github/workflows/code-rules.yml`, which runs `code-rules library check` on every pull request. See [Check changes in CI](https://code-rules.fabricahq.com/guides/version-rules/#check-changes-in-ci). (#71, #73)

### More ways to choose rules

- Import single rules without the rest of their group with the source's `rules` list, or `code-rules project add library --rules RULE`. (#71, #74)
- Import exactly what one library release published with `ref: release/<number>`. (#71, #74)
- Library authors can choose group IDs from the [canonical group list](https://code-rules.fabricahq.com/concepts/groups/#canonical-group-ids), so tools can show the same technology or practice together across libraries. (#86)

## ⬆️ Improvements

- `code-rules project init` now ends by telling you to connect your coding agent, and the managed `.code-rules/README.md` shows the section to add to `AGENTS.md`, `CLAUDE.md`, or your agent's instruction file. `code-rules project init --help` explains what init creates and what running it again does. (#70)
- Code Rules never shows text from Git, Git servers, or `gh`, which can contain credentials. Its errors name the likely cause and give an error code instead, and it hides credentials in repository addresses it displays. (#71, #83)
- Human output, prompts, and errors show control characters as visible escapes, so text from a library can't rewrite what your terminal displays. (#71, #81)
- An invalid answer at a prompt lists the valid answers, and a missing required input without a terminal names the flag to pass. (#71)
- Projects import only the shared `assets/` files that their selected rules link to, instead of the whole directory. (#71, #79)

## 🐛 Squashed Bugs

- Error messages started with a blank line, and new rule drafts had an extra blank line after their metadata. Both are gone. (#71, #83)
- The notice in `generated/provenance.json` said to run project commands from the project root, although they work from any subdirectory of a Git repository. It now says so. (#71, #76)

## ⛓️‍💥 Breaking Changes

Code Rules doesn't migrate projects or libraries for you: configuration fields it no longer supports fail as unknown fields, and older vendored snapshots fail as unsupported.

### Projects: update your configuration and import again

Do this once in every project that imports libraries.

1. **Edit each source in `.code-rules/config.yaml`.**
   - Delete `version`, the version range. It now fails with `unknown field version`. The source then follows each rule's newest version when you run `code-rules project update`. To stay on one library release, set `ref: release/<number>` instead.
   - Delete `replace`, including an empty `replace: {}`, which `code-rules project add library` used to write. Move each entry into `exclude`, renaming `file` to `replacedBy`.
   - Rewrite each `exclude` value as an object: `rule-id: Reason.` becomes `rule-id: {reason: Reason.}`. An empty `exclude: {}` is no longer needed.
   - `ref` is now optional. It still accepts a tag or a full commit SHA, but not a version range, and you can't combine it with `pins`.
   - If the library hasn't published a `release/<number>` tag yet, keep a `ref` to a tag or commit. Without one, the import fails with `releases-not-found`. Rules imported this way have no version, and `code-rules project sync` warns about them.

   Before:

   ```yaml
   sources:
     team:
       repository: https://github.com/example/rules.git
       version: ">= 1.2.0, < 2.0.0"
       groups:
         - practices/testing
         - techs/typescript
       exclude:
         practices/testing/avoid-snapshot-tests: Contract snapshots follow our own review policy.
       replace:
         techs/typescript/prefer-type-aliases:
           file: local/techs/typescript/prefer-interfaces.md
           reason: Our public extension API relies on declaration merging.
   ```

   After:

   ```yaml
   sources:
     team:
       repository: https://github.com/example/rules.git
       groups:
         - practices/testing
         - techs/typescript
       exclude:
         practices/testing/avoid-snapshot-tests:
           reason: Contract snapshots follow our own review policy.
         techs/typescript/prefer-type-aliases:
           reason: Our public extension API relies on declaration merging.
           replacedBy: local/techs/typescript/prefer-interfaces.md
   ```

2. **Import your libraries again.** Snapshots that v0.1.0 wrote fail with `unsupported source record`. Delete them and sync:

   ```sh
   rm -rf .code-rules/vendor/
   code-rules project sync
   ```

   This sync imports every rule at its newest version, except pinned rules and sources that set `ref`, so it can move rules past the versions your project used. To keep what you had, set `ref: release/<number>` or pin rules before you sync.

3. **Commit** `.code-rules/config.yaml`, `vendor/`, and `generated/` together.

The new configuration format is in the [configuration reference](https://code-rules.fabricahq.com/reference/configuration/). (#71, #74, #76)

### Projects: how commands behave

- **`code-rules project sync` no longer moves rules to newer versions.** It restores the versions recorded in `vendor/<source-name>/_source.json`. Adopt newer versions with `code-rules project update`, which previews them first, or `code-rules project update --yes` in scripts and CI.
- **`code-rules project add library --ref` is optional and rejects version ranges.** Scripts that passed a range should drop `--ref`, or pass `--ref release/<number>`.
- **Code Rules refuses a `vendor/<source-name>/_source.json` that was changed by hand or in a merge resolution.** Restore the file with `git checkout -- .code-rules/vendor/<source-name>/_source.json`, or with `git checkout --ours` or `git checkout --theirs` during a merge conflict, then run `code-rules project sync` to apply your configuration changes.
- **The managed project guide changed.** `.code-rules/README.md` now has a "Connect your coding agent" section and describes pins and `code-rules project update`. `code-rules project build`, `code-rules project sync`, and `code-rules project init` replace an older guide you haven't edited, and `code-rules project check` reports it as outdated until then. They refuse to overwrite an edited guide and stop with `unrecognized or manually edited project guide`: move your notes to another file, move the guide aside, and run the command again.
- **Generated guidance shows rule versions.** Each imported rule shows `Version: X.Y.Z` below its ID, `RULES.md` asks reviewers to cite a rule's version with its ID, and `generated/libraries/<source-name>/README.md` lists the library release, rule versions, and pins. `code-rules project check` reports these files as stale until you sync.

(#70, #71, #76, #77)

### Libraries

- **Projects import rule versions only from `release/<number>` tags.** Code Rules ignores other tags, such as `v1.0.0`, when it chooses versions. Until a library publishes its first library release, projects that import it without `ref` fail with `releases-not-found`. From an up-to-date checkout of your default branch, publish it with:

  ```sh
  code-rules library release --dry-run
  code-rules library release
  ```

  The first library release gives every rule version `1.0.0`. Don't create `release/<number>` tags by hand.
- **After the first library release, every rule change needs a change note.** Record each one with `code-rules library change`. The `changes/` directory is reserved for change notes.
- **`code-rules library check` and `code-rules library add rule` need the full Git history and tags.** They fail in a shallow clone with `shallow-clone`, and in a clone that has change notes but no `release/<number>` tags, such as one made with `git clone --no-tags`, with `missing-release-tags`. In CI, check out with full history, such as `fetch-depth: 0` with `actions/checkout`.
- **Add the new check workflow.** Run `code-rules library init` again in an existing library to add `.github/workflows/code-rules.yml` without touching other files. It never changes an existing workflow: to move the workflow to a newer Code Rules later, delete it and run `code-rules library init` again.
- **The library README that `code-rules library init` wrote isn't refreshed** and still says to publish a plain Git tag. Replace its release section with the new guide's, or delete the README and run `code-rules library init` again.
- **License and notice files can't be part of a rule.** `code-rules library check` rejects a `rule-library.yaml` that declares a rule's Markdown file or a file in a rule's asset directory as a license or notice file, and projects refuse to import such a library release. Move the file to the library root or the library-root `assets/` directory, and update `license.file` or `license.notices`.
- **Projects get library-wide files from one library release per source.** Group metadata, shared assets, and license files come from the newest library release when a project adds the source or updates the whole source, even when no rule changes. A pinned rule can therefore link to a newer shared file, so keep everything that defines a rule's obligation in the rule itself.

(#71, #73, #75, #79)

### Scripts and tools that read output

- **Exit codes:** an interrupted command, such as one stopped with Ctrl-C, exits `130` instead of `1`. Usage errors still exit `2`, and now all have the error code `invalid-arguments`.
- **Error codes:** Git and import failures now have an `error.code`, such as `releases-not-found`, `version-not-found`, `connection-failed`, `not-found-or-no-access`, or `git-failed`. Scripts that treated any `code` as a file-writing error should check its value. A `ref` that names a branch fails with `ref-is-branch` instead of `version-not-found`.
- **`code-rules project check`:**
  - In JSON, `value.status` is `up-to-date` or `out-of-date` instead of `up_to_date` or `out_of_date`, and a stale check's `error.kind` is `out-of-date`.
  - Problem kinds are `missing-file`, `stale-contents`, `unexpected-file`, and `outdated-readme`, and each problem's `nextStep` string is now `nextSteps`, a list of `{instruction, commands}` objects.
  - An out-of-date check prints only its report on stdout, without a leading `Error:` line.
- **`code-rules library check`:** JSON `value.groups` and `value.rules` are renamed `value.groupCount` and `value.ruleCount`.
- **Authoring commands** (`code-rules project init`, `code-rules library init`, the `add` commands, and `code-rules library change`):
  - JSON `value.files` is replaced by `value.added` and `value.changed`.
  - JSON `value.next` is gone; use `value.nextSteps`.
  - Human output lists files under `Added:` and `Changed:`, relative to your working directory, instead of absolute paths under `Updated files:`.
- **Lists in JSON are always present**, empty when there's nothing to report, including `value.warnings` and a next step's `commands`.
- **`generated/provenance.json`:**
  - `sources[]` drops `version`, `resolvedTag`, and `resolvedVersion`, and adds `pins`, `release`, and `ruleSelection`.
  - `rules[].origin` and `rules[].upstream` add `version` and `release`, which are `null` for local rules and unreleased imports.
  - `rules[].basedOn` is new: the library version a local replacement is based on, or `null`.

  See the [provenance reference](https://code-rules.fabricahq.com/reference/provenance/).
- **`vendor/<source-name>/_source.json`** uses format version 2. It records each rule's `version`, `release`, and `commit`, and drops the source's `version`, `resolvedTag`, and `resolvedVersion`.

(#71, #76, #83)
